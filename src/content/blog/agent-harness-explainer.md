## 执行摘要：一条主线，四个层次

2025 到 2026 年，大模型最深刻的变化不是说得更好，而是能动手做事了。从 ChatGPT 发布至今，模型在语言能力上的进步有目共睹，但真正打开想象空间的，是模型走出对话框、去触碰真实世界的工具和系统。而实现这一步的，往往不是模型本身，是包在模型外面的那层工程。

这份文档沿一条主线，把这层工程拆成四块来讲：Agent 范式、Harness 运行骨架、Hermes Agent 自托管框架、openclaw 应用形态。由抽象到具体，由原理到落地。

**核心结论**

- **Agent 是范式**：把无状态模型放进「感知 → 决策 → 行动 → 观察」的闭环里，它才从答题者变成执行者。没有这个闭环，模型再强也只是纸上谈兵。
- **Harness 是骨架**：负责主循环、上下文管理、工具调度与权限控制。Claude Code、openclaw 本质都是智能体的运行时。模型出脑子，harness 出身子。
- **Hermes Agent 是自托管框架**：Nous Research 于 2026 年 2 月开源。模型无关，数据本地优先。最特别的是它的闭环学习机制：每完成一个复杂任务，自动沉淀为可复用的 skill，越用越强。发布后迅速积累超过 18 万 GitHub star，是 2026 年开源 Agent 生态中势头最猛的项目之一。
- **openclaw 是应用形态**：把智能体从终端搬进聊天软件，让你像发微信一样指挥它。2026 年初发布后迅速走红，GitHub star 突破 37 万，是近年增速最快的开源项目之一。

> **本文档试图回答四个问题**：一个模型怎么才算成了 Agent？Harness 到底替模型扛了哪些活？Hermes Agent 凭什么能越用越强？openclaw 又把这套骨架做成了什么样的产品？

四个名词常被混在一起讨论，但它们落在不同层。层分清楚了，选型时就不会拿模型的问题去怪框架，也不会指望换一个框架解决模型的短板。

## Agent：从「会说」到「会做」

Agent 不是一个更大的模型，而是一个被放进闭环里、能自己决定下一步动作的模型。差别不在参数量，在于它有没有一条「行动 → 观察 → 再行动」的回路。一个 4000 亿参数的模型如果只用单轮对话，它仍然是死的；一个 70 亿参数的模型配上正确的循环，它可以是活的。

### 对话与智能体的分界

传统对话是单轮补全：给一段输入，模型吐一段文字，结束。它不知道自己说得对不对，也碰不到外部世界。就像一个被锁在房间里的人，只能对着墙壁说话。

Agent 把这条直线掰成了环。模型每说一句话，都可能是一个动作指令。这个动作会被实际执行，执行结果再喂回模型，让它判断下一步该怎么走。模型因此第一次能"看到"自己行为的后果，并据此修正。这不是量的提升，是质的变化。

还有一个值得对比的范式：**Plan-and-Execute**（先规划后执行）。模型先一次性生成完整的执行计划，再逐步骤落实。它适合步骤明确、中途变数少的任务，比如"把这份数据的 A 列和 B 列合并、去重、导出 CSV"。但现实中的复杂任务往往不是这样。你跑完第一步，输出可能完全出乎意料，原来的第二步就成了废纸。Plan-and-Execute 在这种场景下显得僵硬。因此多数框架以 **ReAct 为默认模式**，把规划能力作为辅助嵌入到循环之中：在每一步推理时自然纳入对整体方向的判断，而不是提前锁死一条路线。

### 最小回路：推理与行动交替

这套回路最经典的表述是 **ReAct**（Reasoning + Acting），由 Yao 等人于 2022 年首次系统提出。核心思想不复杂：让模型把"想一步"和"做一步"交替进行。一轮 Agent 循环可以归结为四步：

1. **感知**：读入任务目标和当前可见的环境状态，包括已有的对话、文件内容、上一步工具返回的结果。
2. **推理**：模型判断下一步该调用哪个工具、传什么参数。这一步是所有"智能"的集中体现。
3. **行动**：工具被真正执行。读文件、跑命令、调 API、写数据库。这是模型第一次触碰到真实世界。
4. **观察**：执行结果写回上下文，模型据此决定再走一步还是收尾。如此往复，直到任务完成。

> 这里有一个极易被忽略但至关重要的细节：模型自己不会执行任何动作。它只会输出"我想调用某个工具"这个意图，一段结构化的 JSON，仅此而已。真正去跑命令、接结果的，是模型外面那层代码。这层代码就是下一章的主角。

### 为什么模型本身不够

单独的大模型是一个无状态函数：输入文本，输出文本，调用之间什么都不记得，也没有任何手脚去触碰外部系统。你可以用提示词引导它装成一个 Agent，告诉它"你现在是 xxx，你有这些工具可以用"，但它不知道时间过去了多久，不知道你上一轮让它做过什么，更不知道那些动作是否真的被执行了。这种"假装 Agent"和真正的 Agent 之间有本质的区别，需要外部补上三样东西：

- **跨轮次的记忆**：让模型记住在这一轮对话里做了什么、结果如何、当前到哪一步了。
- **可调用的工具**：文件系统、命令行、浏览器、API。没有工具就没有行动能力。
- **驱动循环的运行时**：让上述两者在一个持续的循环中运转起来，而不是跑一步就散了。

这三样都不在模型的权重里，而在它外面的运行层。理解这一点，整个技术栈的分层就自然浮现出来。

## Harness：让智能体转动起来的骨架

Harness，直译"挽具"，本来是指驾驭牲口用的那套绳索和皮带。用在 Agent 语境里，它是一个精准的比喻：模型给你脑子，harness 给你身子和动手的能力。你日常用的 Claude Code 是一个 harness，本章要讲的 openclaw 也是一个 harness。它们形态各异，干的却是同一类活：把一堆无状态的 API 调用编织成一个能持续运转、能自主决策的系统。

### Harness 替模型扛下的四件事

模型只管"下一步该干什么"。剩下让循环转起来、不转崩的工程，全落在 harness 里。它的职责可以收敛为四类，缺任何一样整个 Agent 都不成立：

| 职责 | 具体做什么 | 不做的后果 |
|------|-----------|-----------|
| **循环控制** | 反复调用模型，直到本轮没有新的工具调用为止 | 模型只能答一次，无法完成多步任务 |
| **上下文管理** | 把历史消息和工具返回按窗口大小拼装、压缩、截断 | 对话一长就超出窗口，请求直接报错 |
| **工具调度** | 解析模型给出的调用意图，真实执行，结果回灌 | 模型说要调工具，没人真去执行 |
| **权限与安全** | 在不可逆动作前拦一道，人工审批或沙箱隔离 | 模型一句话就能删库、发邮件、花钱 |

这四件事中，上下文管理往往是实际工程里最棘手的一块。不仅因为窗口有限，更因为"丢什么、留什么"直接影响 Agent 每一步的决策质量。这个问题在第三节展开。

### 主循环：整套范式的心脏

把上面四件事压成代码，就是所有 harness 共用的同一个骨架。一个"调模型 → 执行工具 → 回灌结果"的 `while` 循环：

```python
# harness 主循环：把无状态模型驱动成有状态 agent
messages = [system_prompt, user_task]
while True:
    response = model.generate(messages, tools=TOOLS)   # 1. 调模型，附上可用工具清单
    if not response.tool_calls:                          # 2. 无工具调用 → 任务完成，退出
        return response.text
    for call in response.tool_calls:                     # 3. 逐个执行模型请求的动作
        result = dispatch(call.name, call.arguments)     #    真正干活、碰外部世界的地方
        messages.append(tool_result(call.id, result))    # 4. 执行结果写回上下文
    messages = compact_if_needed(messages)               # 5. 窗口快满就压缩，再进入下一轮
```

这二十行不到的循环，就是"Agent"一词在工程上的全部含义。框架之间的差异都是在这个骨架上做加法：是否并行执行多个工具调用、怎么压缩上下文才能不丢掉关键信息、权限在上一步还是这一步拦截。但骨架本身，从最简陋的个人项目到最复杂的生产系统，几乎一模一样。

这里还要提一个重要背景：Anthropic 于 2024 年底推出的 **MCP（Model Context Protocol）**，试图用统一的标准协议来规范 Agent 与外部工具、数据源的连接方式。它的核心洞察是：如果每个 harness 都要自己实现一遍对接文件系统、对接 API、对接数据库的逻辑，那生态永远碎片化。MCP 相当于"工具调用的 USB 接口"，一套标准，插上就能用。MCP 在协议层对 harness 的部分工作做了标准化切分，让框架作者可以把更多精力放在循环与上下文上，而不是反复造工具对接的轮子。

### 上下文工程：Harness 最难的一环

模型的上下文窗口是有限且按量计费的。任务稍微一长，历史消息和工具返回就会迅速把窗口塞满。因此上面代码里第 5 步 `compact_if_needed` 往往是一个 harness 里最见功力的部分：哪条旧消息可以丢弃？哪条需要做成摘要保留？从外部检索到的资料该放多少进窗口、什么时候放？

这件事在业界被称作**上下文工程**（Context Engineering），即围绕"往窗口里放什么、丢什么、怎么放"做的系统化取舍。它的影响常常不亚于换一个更强的模型：窗口塞满了冗余信息，再强的模型也做不出正确决策；窗口放对了关键线索，中等模型也能出彩。

> 判断一个产品"是不是真 Agent"，不看它接的模型多大，看它有没有这个主循环、能不能在工具执行失败后自己重试或换条路。没有循环的，只是给模型答案套了一层 UI 壳；有循环的，才谈得上自主。

主循环、上下文、工具调度、权限。这套骨架听起来抽象，但在每一个真实产品里就是这样搭起来的。接下来两章用两个 2026 年走势最猛的开源框架做实例：先看重度自托管、主动进化的 **Hermes Agent**，再看把 Agent 无缝嵌入日常聊天的 **openclaw**。看完这两个，你对前面的抽象会有具体的对照。

## Hermes Agent：会自我进化的自托管框架

Hermes Agent 是 Nous Research 于 2026 年 2 月开源的自托管智能体框架。它把上一章那套 harness 骨架做成了完整的产品，模型无关，数据全留在你的机器上。还加上了一件几乎所有框架都没有的东西：让 Agent 越用越强的闭环学习。多数 Agent 关掉就忘，它关掉再开时还记得你，而且比上一次更会干活。

### 先分清：是框架，不是那个同名模型

Hermes 是一个系列名，不是一组权重。Nous Research 发布过 Hermes 系列大模型（在 Llama 基础上微调），但 Hermes Agent 是另一码事，它是一套运行框架，不是模型。框架本身刻意做成模型无关：接 Claude、GPT、Gemini、Hermes 系列或任意兼容 OpenAI 接口的服务都行。Hermes 模型可以做它的底座，但你完全可以用自己的模型替换掉。

框架采用 MIT 许可，发布后迅速积累超过 18 万 GitHub star，是 2026 年开源 Agent 生态中增长最快的项目之一。

### 三层架构与核心构件

Hermes Agent 把用户界面、Agent 核心逻辑、执行后端三层解耦。这不是教科书式的分层画图，而是在代码里清晰地拉开了边界。读懂它的构件，差不多就读懂了一个成熟 harness 的完整解剖：

| 构件 | 职责 |
|------|------|
| **工具注册表** `tools/registry.py` | 框架的核心枢纽。内置 40+ 工具和一个工具集系统，附带约 70 个可供安装的 skill。每个工具文件在导入时自注册，注册表统一做 schema 收集、分发、可用性检查与错误包装。这套机制让工具的添加和删除极其干净：加一个文件就够了，调度代码不用改。 |
| **执行后端** | 同一个工具可以落到多种环境。仅终端就有 6 种后端：本地、Docker、SSH、Daytona、Modal、Singularity。此外还有浏览器、Web 和 MCP 后端。这意味着你可以让 Agent 在沙箱里跑危险命令，同时在不同机器上跑常规命令，而调度代码完全一样。 |
| **会话存储** | 基于 SQLite，搭配 FTS5 全文检索。会话带血缘追踪，压缩前后的父子关系可追溯。按平台隔离、原子写入。这比大多数 Agent 框架的会话管理先进了一代。 |
| **网关进程** | 一个长驻进程对接约 20 个平台适配器，统一处理会话路由、用户授权、命令分发，以及 hook 和 cron 定时任务。 |

这套注册表正是主循环里 `dispatch()` 一步的真身：工具如何登记、参数 schema 怎么收集、执行落到哪个后端，全在这里裁决。

```python
# 每个工具文件在导入时自注册到中央注册表
@register_tool
def run_terminal(cmd: str, backend: str = "local") -> str:
    """在 6 种后端之一执行命令"""
    return BACKENDS[backend].run(cmd)

# 注册表统一收集 schema、按名分发、可用性检查、错误包装。
# 主循环只管调 dispatch(name, args)，不关心工具在哪台机器上跑。
```

这种设计让主循环的代码保持了极度的简洁。它不需要知道终端有几种后端、每种后端的差异是什么。新增一种执行环境，只需要在注册表加一个条目，主循环一行不用动。这是好的架构该有的样子。

### 闭环学习：凭什么「越用越强」

这是 Hermes Agent 最有辨识度的设计，也是它和几乎所有其他 Agent 框架拉开距离的地方。

大多数 Agent 是无状态的。你关掉它，它就忘了你。下次再打开，一切从零开始。Hermes Agent 把学习循环做成了架构的一等公民：每完成一个复杂任务，Agent 会自动生成一个可复用的 skill 文件，把这次任务中学到的操作路径和领域知识沉淀下来。下次遇到类似任务，它直接调用学过的技能，跳过摸索阶段，收敛速度大幅加快。

再加上跨会话的持久记忆与 FTS5 全文检索，它对上下文的理解随使用时间不断累积。不是线性增长，而是每学一个新技能就多了一条可复用的捷径。

这种设计从根本上改变了 Agent 的行为模式：对于反复出现的任务类型，它不需要每次都从零摸索，而是越用越快、越用越准。这也是 Hermes Agent 在长期运行场景下相比其他框架的核心优势所在。

### 怎么跑、还能拿来做什么

部署门槛被刻意压得很低：一条 `curl` 命令自动装好全部依赖，支持 Linux / macOS / WSL2。小到一台 5 美元的 VPS 就能跑，大到 GPU 集群或 serverless 场景也行。数据所有处理都在本地完成，可以直接对接本地守护进程或开发环境，不需要 ngrok 之类的隧道转发。对安全要求高的场景，这一点尤为重要。

此外它还有一项开发者友好的功能：批量生成工具调用轨迹的能力，可以自动 checkpoint 并导出，用于微调模型。对想要自己训练 Agent 模型能力的团队来说，这意味着把一大段手工构造训练数据的流程自动化了。

Hermes Agent 把 harness 推到了"重度自托管 + 自我进化"这一端。下一章的 openclaw 代表了同一类骨架的另一种取舍：更轻、更贴近日常聊天，门槛更低。

## openclaw：把骨架装进日常

如果说 Hermes Agent 是一间装备齐全的私人实验室，openclaw 就是把实验室的核心功能塞进你手机上聊天 App 里的那个按钮。它是 harness 的一种完整产品形态，把智能体从开发者的终端搬进你每天都在用的聊天软件，让你像发消息一样指挥它干活。2026 年初发布后迅速走红，GitHub star 数突破 37 万，是近年增速最快的开源项目之一。

### 它是什么

openclaw 是一个跑在你自己机器上的开源 AI 助手，前身名为 Moltbot / Clawdbot，由 Peter Steinberger 与社区共同构建。几个决定了它产品气质的选择：MIT 许可、本地优先（记忆和数据以 Markdown 文件存在你的本地磁盘上）、一套可移植的技能格式让社区可以自由扩展。它能代你执行 shell 命令、做浏览器自动化、收发邮件、读写日历和文件。正因为接入的是真实的消息平台和本地系统，它的能力边界和潜在风险都比一个普通的聊天框大得多。

### 网关架构：单一真相源

openclaw 的核心是一个自托管的网关（Gateway）。它的一头连着各种聊天渠道：Telegram、WhatsApp、Slack、Signal、Discord 等等。另一头连着一个或多个 AI 编码智能体。网关是整个系统的单一真相源：谁发来的消息、消息归属哪个会话、该交给哪个 Agent 来处理，全部在这里集中裁决。

这个设计好在一个简单的地方：如果没有网关，你要在每个聊天平台各自配置一遍 Agent 的路由和安全策略。Telegram 设一套，Discord 设一套，Slack 再设一套。出错概率高，维护成本更高。网关把这件事做了集中化，支持多 Agent 路由，按 Agent、工作区或发送者做会话隔离，互不串扰。

![openclaw 网关架构图：外部聊天渠道（Telegram / Slack 等）经入站/出站箭头连接到网关核心，网关将任务路由到不同的后台 Agent 会话（Claude Code / Codex 等），同时读写本地 Markdown 记忆文件。](/assets/openclaw-gateway.svg)

*图 2：openclaw 网关架构。所有渠道与 Agent 会话都经网关路由。会话隔离、定时唤醒、权限审批可以集中实现，不必在每个聊天平台各做一遍。*

### 让 Agent 自己动起来：定时调度

openclaw 内置了定时任务能力，可以按可配置的间隔自动触发 Agent 执行。比如定时查收邮件、盯任务进度、跑定期巡检，不需要你开口触发。

一个只会"你问一句、它答一句"的系统是助手。一个没有人催也会按节拍自己动的系统，才是自主智能体。从被动响应走向主动执行，这是 Agent 在产品体验上的质变。听起来玄，实现上就是一个定时器加上一段可配置的任务描述，但加不加这一笔，产品给用户的感受截然不同。

### 把编码智能体接到聊天里

openclaw 最实用的场景之一，是把 Claude Code、Codex 等编码智能体作为后台会话进行管理。通过网关的多 Agent 路由能力，它可以将编码任务分发到隔离的 worktree 中执行，在编码 Agent 之上叠加了会话生命周期管理、唤醒路由、隔离执行与结果回传。

于是你可以从 Telegram 或 Discord 发起一个编码任务，比如"修一下那个测试"，然后在第一条消息之后持续观察进展：改了哪些文件、跑了什么测试、出了什么错、什么时候修好的。整个过程都不需要你打开终端。

```bash
npm install -g openclaw@latest
openclaw onboard --install-daemon   # 引导配置并装成后台守护进程
```

### 先谈安全，再谈能力

> openclaw 连着真实的消息平台和你的本地系统，安全不是可选项，是前置条件。官方给出的几条底线值得认真对待：在服务商一侧设硬性消费上限；任何不可逆动作（支付、删除、发邮件、对外操作）必须挂一道人工审批；锁定到近期的安全版本并持续更新；除非你清楚自己在做什么网络配置，否则不要把它暴露到公网。所有入站消息都应视为不可信输入。

讲到这里，四层各自亮了相。但它们真正的威力在于咬合在一起。下一章用一个完整请求，把四层从头到尾串一遍。

## 四层如何咬合：一次完整调用

分层把职责说清楚了，但只有把它们串成一次真实请求，才看得出这套设计的精巧。设想一个场景：你在手机上发一句"帮我把仓库里失败的测试修好"。看这句话怎么穿过四层、又怎么带着结果回来。

1. **应用层 · 接入**：你在 Telegram 发出这句话。openclaw 网关收到消息，按你的发送者身份路由到对应会话，选定后台的一个 Claude Code 智能体来接手。
2. **框架层 · 组装**：Harness 把任务描述、仓库当前状态、可用工具清单组装成上下文，启动主循环。每个工具的 schema 随请求一并提交给模型。
3. **模型层 + 协议层 · 决策**：模型读完上下文，推理出第一步应该跑测试。它按照函数调用格式吐出一个结构化的 `tool_call`，比如 `run_tests`，附带目录路径和目标文件。注意：到这一步为止，测试还没有真的被执行。
4. **框架层 · 执行回灌**：Harness 接住这个调用，`dispatch("run_tests", {...})` 真正跑起来。测试失败，输出完整的异常堆栈。Harness 把这段输出打包成 `tool_response`，写回上下文。
5. **循环 · 收敛**：模型读到失败堆栈，定位到出错的源文件和行号，吐出下一个调用：修改文件、重新跑测试。Harness 继续执行并回灌。如此往复，直到测试变绿、本轮不再有新的工具调用。
6. **应用层 · 回送**：网关把最终结果连同 PR 链接发回你的 Telegram。整个过程在隔离的 worktree 里完成，主分支从头到尾没被碰过。

> 串起来看，每一层只解决自己那一段：模型负责判断下一步，协议负责把判断说清楚，框架负责真正执行并驱动循环，应用负责接入你的生活并守住权限。任意一层被替换（模型换成更强的、协议换一种格式、聊天平台从 Telegram 换到 Discord），其余三层几乎不用动。这种解耦，正是把"分层"二字从架构图变成工程价值的地方。

> **一句话**：Agent ＝ 模型（会判断）＋ 协议（说得清）＋ 框架（跑得动）＋ 应用（用得上）。少了任何一层，它要么不会动，要么没法用。

## 落地选型与边界

理解了分层，选型就不是跟风挑名字，而是按约束挑层。先看你的硬约束落在哪一层，再决定每层用什么。

### 按约束选组合

| 你的首要约束 | 建议组合 | 原因 |
|-------------|---------|------|
| 要最强通用能力，能接受闭源 | 闭源模型 + 厂商 SDK，或直接用 Claude Code | 省去自建 harness 的成本，循环和工具调度已经成熟 |
| 要重度自托管、希望 Agent 越用越强 | Hermes Agent | 数据全在本地，闭环学习自动沉淀技能，还能当训练数据平台用 |
| 想从手机 / 聊天软件指挥、做个人自动化 | openclaw | 网关已接入多渠道，自带定时调度与多 Agent 路由 |
| 主要在编辑器和终端写代码 | Claude Code、Codex 等终端工具 | 贴着代码库工作，工具和权限模型为编码场景深度优化 |

这四行不互斥。openclaw 把 Claude Code 当后台编码 Agent 跑，就是"应用层 + 框架层"的组合。Hermes Agent 既能独立当框架，也能被别的网关当后台会话调用。分层的意义，正是让你按需混搭，而不会被某个产品名绑死在一个生态里。

### Hermes Agent 还是 openclaw

这两个是 2026 年开源 Agent 浪潮里最像的一对：都自托管、MIT 许可、本地优先、都接了一堆聊天平台、都跑一个网关进程。差别在于它们各自把取舍推向了哪一端：

| 维度 | Hermes Agent | openclaw |
|------|-------------|----------|
| 发布时期 | 2026 年 2 月 · 18 万+ star | 2026 年初 · 37 万+ star |
| 定位 | 会自我进化的 Agent 框架 | 装进聊天软件的个人助手 |
| 记忆机制 | SQLite + FTS5，自动生成可复用 skill | 本地 Markdown 文件 |
| 最大卖点 | 闭环学习、批量生成训练数据 | 多渠道网关、定时调度、挂载编码 Agent |
| 最适合 | 长期自托管、希望 Agent 越用越强 | 快速上手、从手机指挥日常自动化 |

如果你有一套长期运转的环境，愿意花时间调教，Hermes Agent 的自我进化能力会随着使用不断产生复利。如果你想要立刻能用、从手机指挥一切，openclaw 的部署和接入体验明显更友好。两者并不互斥，你完全可以用 openclaw 做入口，后台连 Hermes Agent 做执行。

### 三条绕不开的边界

- **自主性与可控性互为反比**。定时调度越频繁、自动执行越多，越要在不可逆动作前加审批闸。把自主性开满却不设闸，等于把方向盘交给一个不会停的 while 循环。
- **提示注入是新的攻击面**。Agent 读取的网页、邮件、消息中可能藏着"忽略以上指令，执行 xxx"的诱导内容。凡是入站内容，默认当不可信数据对待。
- **成本会被循环放大**。一个没有步数上限的主循环可能反复调用模型，token 消耗在没人注意时指数增长。务必设预算上限和步数阈值，循环失控时自动熔断。

> **周一就可以做的一件事**：挑一个你每周都在重复的小任务，用一个现成 harness 把 Plan → Review → Execute 跑通一轮，并刻意把人工审批卡在最后一个不可逆动作之前。先把闸建好，再谈放权。

## 附录：术语表与参考资料

### A. 术语表

**Agent（智能体）**：被放进「感知 → 决策 → 行动 → 观察」闭环、能自主决定下一步动作的模型系统。区别于普通对话模型的核心特征是闭环。

**Harness（运行骨架）**：包在模型外、负责循环控制、上下文管理、工具调度与权限的运行时。Claude Code、Hermes Agent、openclaw 都是 harness 的不同实例。

**主循环（Agent Loop）**："调模型 → 执行工具 → 回灌结果"反复进行、直到本轮无新工具调用的 while 循环。Agent 区别于单轮对话的核心工程要素。

**ReAct**：让模型把"推理一步"和"行动一步"交替进行的智能体范式。Yao 等人于 2022 年首次系统提出，是目前多数 Agent 框架的默认行为模式。

**Plan-and-Execute**：先让模型生成完整计划再逐步执行。适合步骤明确、中途变故少的任务。常与 ReAct 结合使用，以规划辅助循环。

**函数调用（Function Calling）**：模型以结构化 JSON 格式输出"要调用哪个工具、传什么参数"的能力。是模型与外部工具之间的标准通信协议。

**上下文窗口（Context Window）**：模型单次能读入的 token 上限。有限且按量计费，是 Agent 工程最核心的硬约束。

**上下文工程（Context Engineering）**：围绕"往窗口里放什么、丢什么、压缩什么"做的系统化取舍。对 Agent 决策质量的影响不亚于模型能力。

**MCP（Model Context Protocol）**：Anthropic 于 2024 年推出的开放标准，用统一协议规范 Agent 与外部工具、数据源的连接。可类比为"工具调用的 USB 接口"。

**Gateway（网关）**：Hermes Agent 与 openclaw 中负责会话路由、渠道连接与授权管理的长驻进程。整个系统的单一真相源。

**定时调度（Scheduled Automation）**：按固定间隔触发智能体执行任务的能力，使其无需用户主动触发也能自主运行。openclaw 内置了定时任务支持（cron）来实现这一能力。

**Hermes Agent**：Nous Research 于 2026 年 2 月开源的自托管 Agent 框架。模型无关，以完成任务即自动生成可复用 skill 的闭环学习为核心辨识特征。

**闭环学习（Closed Learning Loop）**：Agent 完成任务后自动将过程与知识沉淀为可复用技能文件，后续相似任务直接调用、跳过重复探索。Hermes Agent 最核心的差异化特性。
